DustGate · exploration · 2026-08-21

Renaming a plug, and taking one off a tool

Two gaps, one row. Today a smart outlet's name is read live off the Shelly and never stored, so it degrades to an IP the moment the plug is offline — and there is no way to change it from DustGate at all. Unpairing exists only as a Yes/No question, and leaves the plug still wearing our name and still pushing at us. This page proposes the paired row that fixes both, and shows the three claim states it has to survive.

Where the name comes from today

Live off the plug, every scan

GET /api/outlets/discover mDNS-sweeps, then asks each hit for its own name — Gen2+ Switch.GetConfig?id=0, falling back to Sys.GetConfig; Gen1 /settings. That is the label you would edit in the Shelly app.

plugclaim::decide strips our · dustgate-shop suffix before it ships, so the picker never shows our bookkeeping and never saves it back doubled.

And then it is thrown away

sensor.outlet stores { gen, ip, thresholdW, host } — no name. The canvas plug row falls back to host || ip, and reopening the pairing sheet on an already-paired tool shows an IP, because plugName is only ever set by picking.

So a plug that is switched off, or paired before the last scan, has no name on screen.

We already rename plugs

On pairing, the firmware writes "<label> · <our-host>" back to the Shelly (SmartOutletControl.cpp:502) so the plug says who owns it in the Shelly app, where no DustGate UI exists to explain it.

You just never get to choose the label half. That is the whole feature.

Removal · what "release" means

Unpair hands the plug back

Three things come off, not one

1. The layout. sensor.outlet goes; the next topology adopt drops the poll slot (firmware.ino:559) and the tool goes manual. This is the only part that happens today.

2. Our name. parseName the current name, write back the label alone — the plug stops claiming to be ours in the Shelly app.

3. Our push target. Restore previousPushUrl if we took the plug from someone, otherwise clear Ws. That field has been stored on every takeover since the claim work landed (SmartOutlet.h:133) and nothing has ever read it.

When the plug is not there

Steps 2 and 3 are blocking HTTP to a device that may be switched off. The unpair must still succeed locally — refusing to let you detach a plug because the plug is unplugged would be absurd.

So: remove it from the layout regardless, and say plainly that the plug keeps our name and push target until it is back. No silent partial success. Try the not responding scenario above for the wording.

Read-only plugs release cleanly

A plug owned by Home Assistant was paired poll-only — we never wrote its name or its Ws config, so there is nothing to hand back. Unpair is purely local, and the confirm should say so rather than implying we are about to touch someone else's device.

The other two places

Tool setup, and the canvas row itself

Tool setup → the selected plug

Setup gets the same row

Once a plug is chosen, the scan list collapses to the paired row above the threshold slider — identical component, identical verbs. Today the list stays open forever with a tick beside the choice, which is why there is nowhere to put a name.

Setup also lies about state on arrival: toCfg() hardcodes hasPlug: true, so a manual tool opens showing Yes. Fix it in the same pass — the toggle should say what is true.

The canvas row stops showing IPs

With a cached label on the outlet, plugOf() reads lastScan.name || outlet.label || host || ip — the live name still wins, so a rename in the Shelly app shows up on the next scan, but an offline plug keeps a human name instead of decaying to an address.

What it costs

The pieces this needs

shop schema sensor.outlet.label A cache, not the source of truth. The Shelly holds the name; this is a display fallback and the live scan always wins.
UI One paired-row component Used by the pairing sheet and by tool setup, so the two cannot drift.
Resolved 2026-08-21

The three open questions, and what they became

yes · built

Rename a plug before pairing it?

The tray chips on the canvas are unpaired plugs, and naming them is exactly when a name is most useful — "which of these four shellyplug-s-… is the jointer". But a long-press on a chip collides with the drag that pairs it. Resolved without a long-press: a plain TAP on a chip with no tool armed was already a dead gesture, so that is what opens the rename. It cannot collide — the branch only runs when nothing moved and nothing is waiting to be paired.

on blur · built

Does rename write immediately, or on Save?

The sheet's Save writes the topology. The Shelly write is a different device and cannot be part of that transaction. Proposed above: the name field writes on blur, with the result in the row — so Save stays a layout action and a failed plug write does not silently roll back a layout edit. Costs an inconsistency if you rename and then Cancel — accepted: the plug is a device on the far side of the LAN and was never inside the transaction to begin with.

yes · built

Collector plug too?

The same sheet runs in switch mode for the collector. Rename applies unchanged; Remove means "I start the collector by hand", which is a legitimate shop the firmware already supports. Confirmed yes, and it needed no extra work: the collector already opens the same sheet in switch mode.

Status

Built 2026-08-21. The outcome is in canvas.html §4 — which did not document the plug row or the tray at all before this — and in decisions D-49/D-50/D-51. Two things changed on the way from this page to the code: the cached name went into the Outlet schema's existing unused name field rather than a new label, and the confirm grew a third wording for "we have no scan data", since promising a clean release we cannot verify is the same dishonesty this page was written to avoid.
