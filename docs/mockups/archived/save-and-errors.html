Save and Error Messages

The canvas's "Saved here, but the controller won't take it yet" said three wrong things at once: it wasn't saved, the shop brain hadn't refused anything, and the reason was written for a developer. A search of the app turned up the same faults in about twenty other places. This page proposes one way to say each of them, and one place for the technical detail to go instead: the browser console.

Sliding gate

2 · Leaving with changes that aren't saved

Leave without saving?

Your changes to the layout haven't reached the shop brain. If you leave, they're gone.

Today: nothing. Leaving the canvas or reloading drops an unsaved draft without a word, which is exactly what "Saved here" let you believe wouldn't happen.

An in-app sheet when you tap away to another screen; the browser's own "Leave site?" for a reload or a closed tab. Shown only when the canvas really has unsaved changes.

3 · The canvas can't read your layout can lose a shop

Couldn't load your layout from the shop brain. It didn't answer. Nothing has been changed, and editing is off until it loads, so nothing can be saved over it.

Today: a blank shop. Any failure to read the layout (the brain rebooting, a WiFi blip) is treated like a brand-new brain with nothing saved, and the canvas offers an empty collector to build on. Add one gate and press Save, and the real layout is replaced.

Only a brain that answers "no layout yet" (HTTP 404) gets the blank starting shop. Anything else gets this, and the canvas stays read-only until a retry works. The Live screen has the same confusion in a milder form: it says "No shop configured yet" when the brain just didn't answer.

4 · Every other message that says the wrong thing

From a read of every error handler in the app (91 of them). Grouped by the mistake, because the fix is one shared helper per mistake, not twenty one-off rewrites.

A. "Couldn't reach" when the brain did answer, and said why

The commonest. The handler can't tell "no answer" from "answered with a refusal", so every refusal reads as a network problem and sends you checking WiFi. The brain's own reason is thrown away. Fix: one helper that says "didn't answer" only when it didn't, and otherwise passes the brain's reason on.

A list fails to load, the handler leaves it empty, and the screen then reports the empty list as the truth. Fix: keep "didn't load" apart from "loaded, and empty", and say the first.

E. Silent, with nothing in the console

About thirty handlers swallow the error completely: background polls (right to stay quiet on screen) but also one-off loads. None leaves anything to debug with. Fix: section 5.

5 · The detail goes to the console

[DustGate] canvas · save: refused (HTTP 400)
  shown:   Not saved — the shop brain refused it: systems not an array.
  request: PUT /api/topology
  answer:  {"error":"invalid topology","errors":[...]}
[DustGate] canvas · save: not saved (validation, 1 issue)
  shown:   Not saved — the sliding gate's board is set up for ball valves…
  issues:  [{code:"controller", ref:"dustgate-slider",
             message:"board \"dustgate-slider\" is set up as a servo board but has a sliding gate on it"}]
[DustGate] Live · poll: no answer (3rd in a row) — said once, then quiet until it recovers

One helper, used by every handler above: it writes the context, the friendly text it showed, and the raw request and answer (or the validator's own issues) as a console.warn, then hands back the friendly text for the screen.

  • Background polls log the first failure and the recovery, not every tick, so the console stays readable.
  • Every line starts [DustGate], so one filter shows them all.
  • Nothing secret goes in: the API key is a request header, and headers aren't logged.

6 · Decide before building

Should an unsaved canvas survive a reload?Keeping the draft in the browser would make "your changes stay" true even across a refresh. Proposed: not yet. Warn on leave (2) instead; a stored draft can quietly go stale against the real layout.
Should a board's last-known type live in the layout?It already does (drives); today's fix stopped a switched-off board from wiping it. Proposed: nothing more.
One banner for all screens, or each its own?Proposed: the canvas gets the banner above; the other screens keep their inline error lines, rewritten through the shared helper (A, B).
