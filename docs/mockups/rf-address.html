Matching the Remote

DustGate presses the dust collector's remote by transmitting its frame. To do that it needs the remote's address — eight bits set by a DIP switch inside the fob. There is no receiver in the product, so the user reads the switch and copies it.

The whole screen is one idea: don't ask a woodworker what an address is. Show them a picture of the switch they are holding and let them match it. The number underneath exists for support calls, not for them.

Decisions

Draw the part, not eight checkboxes

The user is holding a physical switch and copying it. Anything that does not look like that switch makes them translate, and translation is the entire failure mode here. Red body, white nubs, numbers on the package, ON printed along one edge — because that is what is in their hand.

The labelling is the only thing that can be silently wrong

Rocker N is address bit N−1, and ON = closed = grounded = 0. Get that inverted and every address comes out bit-flipped — the transmitter works perfectly, the receiver ignores it, and nothing on any screen looks broken. It is why the drawing has to carry the ON legend in the same place the real part does, rather than a caption saying which way is on.

Show the number, for someone else's benefit

Nobody setting this up needs to see 94. It is there so a support conversation can be "what does it say?" rather than "describe your switches", and so a layout edited by hand and one set here are visibly the same thing. Kept quiet — muted, under the drawing, never the headline.

Getting it wrong is recoverable, not fatal

Reading a DIP upside down reverses the rockers and flips which side is on, so the plausible mistakes are exactly four: as entered, inverted, reversed, both. If the entered address does not answer, the device tries the other three and keeps whichever works — then tells the user which way they read it, so the next one goes right.

Setup only, and this is not a detail. An inverted address is not a nonsense value — it is a valid address belonging to some other receiver. A shop with two collector boxes, or a neighbour within 26 feet, is a shop where trying the alternates can start the wrong machine. Acceptable with someone standing here watching a lamp; never acceptable unattended, which is why the runtime retry policy presses the same address three times and then reports a fault instead.

Test before Save, and test with a lamp

The address is unverifiable by inspection: a wrong one fails silently. So the screen offers one press and watches for the collector's own plug to answer — the closed loop we already built. A lamp in the outlet, not the collector, because a blower takes seconds to spin up and coast down and a lamp is instant and unambiguous.

The receiver has the same switch

An HT12D has to match its encoder, so the receiver box carries an identical 8-way DIP. That is a second place to read the same answer, and it matters more than it sounds: a fob can be lost, glued shut, or painted over, and the receiver is screwed to a wall.

Not a receiver, deliberately

"Learn mode" — listen for the fob and capture its address off the air — needs receiver hardware in every unit for a step performed once. Reading the switch costs nothing and works when the fob's battery is dead. If a later product already carries a receiver for other reasons, this becomes worth revisiting.

What it writes

FieldFromNotes
control.rf.address this screen 0–255. Bit i = rocker i+1, open = 1.
control.rf.data not asked Defaults to the measured 0b1110. A single-button fob asserts one data line; sweeping for it is a bench job, not a setup question.
control.rf.pin not asked A property of how the board is built, not of the user's remote. Comes from the board's default pad.

A collector with control.rf must not also have control.outlet — two ways to command one blower fight each other, and the model already refuses it.

Open

Other remotes are not all HT12E. This screen assumes eight address bits and a DIP. Plenty of collector remotes are rolling-code or fixed-code-with-no-switch, and those cannot be matched this way at all — they need the servo presser (tool-sensing-rfc.md §4.2a), which does not care what the protocol is. Deciding how the setup flow ASKS which kind you have is not designed yet, and is probably the first thing that turns this one screen into a branch.

Multi-button fobs (§4.2b) would need a data word per button, not one. Out of scope here; the servo path handles them more naturally.
