The Gates Screen

A way into gate calibration that isn't the build canvas. Every configured gate in one list, each one tappable into the calibration it already has.

Built 2026-08-21, as dustgate-ui/src/app/gates/gate-list.component.ts on /gates, with a Gates entry in the live view's nav. The calibration it opens (app-selector-config, and the servo and linear calibrators under it) was already there and is unchanged — what was new is only the way in.

Two things moved from the open questions below: Test is in (it swings a gate closed → open → closed and stops), and "last calibrated" is out — it would cost a schema field and a migration to answer a question the calibrated pill mostly answers already. UNTESTED ON HARDWARE: the swing has driven demo servos, never a real valve.

app-selector-config

The existing component, handed this gate and the topology. It already dispatches to the servo calibrator (nudge the handle, capture where it lands — no degrees anywhere) or the linear one (the reference sweep between endstops), and already emits saved / cancelled.

Nothing about calibration is redesigned here. Save returns to the list with the row's pill updated; Cancel returns with nothing written.

What each decision is

One list, not a wizard

"Run through all the gates" could be a forced march — gate 1, next, gate 2, next — the shape tool setup used to have, until it was rebuilt as a list on this pattern (2026-08-22). A list is better because recalibration is almost always about one gate: the valve that got knocked, the one that was never done. A march makes you walk past three working gates to reach it. The list also answers a question a wizard can't: which gates still need doing, at a glance.

The verb changes with the gate

Ball valve / manifold — "Calibrate" or "Recalibrate": teaching one servo where its positions are, by eye, at the gate. Sliding gate — "Run setup again": the reference sweep re-measures the whole rail and replaces every stop, which is a bigger, more disruptive act than nudging one valve. Same button, honest about what it does.

A gate on a dark board is shown, and disabled

Same rule as a claimed board in the boards list: hiding it makes a gate you configured look like it vanished. It stays, with the reason, and the button is out — there is nothing to nudge if the board it lives on isn't answering.

Test may only ever drive SAVED positions

The swing sends the gate's own calibrated values and nothing else — the schema's angle for that state, already clamped to the servo's travel, or a saved stop index for a slider. Nothing is interpolated or assumed, and an uncalibrated gate refuses rather than being given a plausible angle: a clutchless servo driven past its hard stop stalls and cooks. That rule lives in swingSequence() in selector-types.ts, where it is unit-tested without a browser.

One cycle, not a loop, so it cannot run away while nobody is watching, and one gate at a time shop-wide — the same one-servo-at-a-time budget routing keeps. It ends closed: a test that left a gate open would change where the shop rests.

Where the entry point goes

A fourth item in the live view's nav, beside Shop layout / Tools / Settings — the place the app already puts "go somewhere else". Today gate calibration is reachable only by finding the gate on the build canvas and tapping it, which is a layout tool, not something you want to open with a wrench in your other hand.

Open questions

Both answered 2026-08-21. Test is in, and it is the reason the safety rule below exists. "Last calibrated" is out — a schema field and a migration to answer a question the pill mostly answers already.

Still open: whether a test belongs on the Live view's tool rows too, where you are already looking when a tool doesn't pull.
