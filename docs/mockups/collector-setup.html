Setting up the Collector

One sheet for the one machine DustGate is allowed to command. It replaces the single-slot plug pairing the canvas opens today, which can only ever say this plug switches the cyclone — and so cannot describe the collector actually on the bench: switched by its remote, watched by a metering plug, with a beam across the bin.

Two questions, never one. How is it switched and how is it watched are independent, and fusing them is what the current screen got wrong. Every way we now command a collector except a plug is stateless — a servo arm, an RF frame — so what we sent proves nothing, and something else has to say whether the blower is actually turning. The model has said this since the day control and sensor were split apart; only the UI never caught up.

Decisions

    


      

        
Switching and watching are separate questions

        

          The screen this replaces asked one: which plug switches this? That is only
          answerable for a collector on a switchable Shelly, and the collector on the bench is
          not one. Worse, the single gesture the canvas offers — drag a plug onto the cyclone —
          writes control.outlet unconditionally, so dropping the shop's metering
          plug there produces a document the model then rejects: a no-relay plug named as
          a switch is a collector that can never start.
        

      


      

        
A plug answers both questions, and the screen says so rather than asking twice

        

          Choose Smart plug and the watch question collapses to one locked row naming that
          same plug. It is not a third state to configure — a Shelly reports its own power — and
          offering a second plug there would invite someone to pair two plugs to one blower.
          This is the one case where the two questions have one answer, which is exactly
          why they must still be drawn as two: it is a property of that hardware, not of
          collectors.
        

        

          The firmware already behaves this way — TopologyRuntime::collectorSensorOutlet()
          falls back to the control plug when sensor.outlet is absent — so the collapsed
          row is describing what happens, not deciding it.
        

      


      

        
Open-loop is allowed, and says so where you can see it

        

          A press with nothing watching is a real configuration — a shop that has not bought a
          plug yet — and the model permits it deliberately. But a press is an edge against a
          toggle: get one wrong and the system's belief and the blower disagree until a
          person notices. So it warns, in the sheet, at the moment the combination is chosen,
          rather than at save time or in a log nobody opens.
        

      


      

        
The unbuilt paths are drawn, greyed, and dated

        

          A servo on the collector's own paddle is the path the RFC now aims at (§4.2c), and the
          CT clamp is the answer for a 240 V machine with no plug to pair. Neither exists. Showing
          them as disabled rows with a reason beats hiding them: it tells the reader the sheet has
          room for the case they are in, and it stops the next person designing a fourth screen
          for the same question. A greyed row must say what it is waiting for, or it reads
          as broken.
        

      


      

        
The bin is a toggle plus a board, not a wizard

        

          A diffuse beam answers dust at this height, y/n. There is no range, no percent,
          no calibration — so there is nothing to walk anyone through. The only real question is
          which board is it wired to, the same question a gate asks, and the answer is the
          board at the collector essentially always. invert is not asked: it is a
          fact about how the sensor is wired, settled in the wiring doc, not a user preference.
        

      


      

        
The remote row shows the switch, not the number

        

          address: 94 is true and useless: a woodworker has no reason to know what
          eight bits are, and a row that prints a number invites them to believe it is something
          they should understand or change. So the summary row draws the part — the same
          eight rockers they matched during setup — and says matched to your remote.
          rf-address.html keeps the number, on purpose and for a
          different reader: it is the one thing a support call can ask for over the phone. The
          rule that reconciles them is that the number is for someone helping you, the picture
          is for you.
        

      


      

        
A full bin flashes every board on that system, in red

        

          The strobe on the cyclone can only mean this sensor tripped, and it is in one
          place — which is no use at the far end of a shop with a tool running. So the alert fans
          out to the pixel every board already carries, and the sheet says so at the moment you
          switch the bin on, because "what does enabling this actually do" is otherwise invisible.
        

        

          Red is right, and the blink is what keeps it honest.
          StatusLed.h reserves red for a fault the board cannot fix itself, which a
          full bin exactly is — and its own rule says blink rate may be a second-order detail
          inside a colour, never the signal. So: steady red still means this board is
          broken, flashing red means the bin it serves is full. Without that split, five healthy
          boards going red reads as five dead boards.
        

        

          System, not shop. The boards are derived — collector → system → elements →
          selectors → controllerIds — so only the primary can resolve the set, and a second
          collector's boards stay dark for a bin that isn't theirs. An alert that cries wolf gets
          ignored, and this is the one alert that must not be.
        

      


      

        
Coast-down lives on the collector, and only there

        

          This card has now said three things, which is worth recording rather than tidying
          away. It began as "coast-down moves here"; building it changed that to "both screens
          are fine, because both write the same field on the same element and there is one
          value"; and Jeff settled it back the other way on 2026-09-14 — tie it to the
          collector and remove the global setting.
        

        

          The middle position was not wrong about drift. It was wrong about what a settings page
          is FOR: a shop-wide screen listing one row per collector is not a convenience, it is a
          second place to learn that collectors differ. The same argument took Port size
          out with it — that one was worse, because it was a single shop-wide value feeding a
          per-rack decision, and a shop can hold a 2½" rack and a 4" one.

Open

    

      

        SETTLED while building, 2026-09-14 — the drag routes by the plug. A dropped
        Tasmota can only ever be a watcher, because naming a no-relay plug as the switch
        describes a collector that can never start and the model rejects the document. A
        dropped Shelly becomes the switch, which is the only thing it could have meant before
        this sheet existed. Either way the collector's glyph opens this sheet on a tap — and it
        does so now even with no plug at all, which an RF-pressed collector has, or the only
        screen that can configure a remote would be unreachable from the canvas.
        setOutlet() in shop-doc.ts, with the cases in its spec.
      

      

        The red flash needs a frame that does not exist. The primary reads its own bin pin
        and can colour its own pixel today. Telling the OTHER boards on that system to flash is
        primary→node, which is the direction NodeLink already runs — but there is no frame for an
        alert, only for resolved moves. That is a smaller piece of work than the node→primary bin
        report (which is a genuinely new direction), and it is the half that makes the sheet's
        promise true.
      

      

        The bin has nowhere to be seen. This sheet configures it; no screen reports it.
        systems[].bin has been on the wire since 2026-09-04 and the live page does not
        read it. That is a second design, not this one — but it is the reason to build this one
        carefully, because a bin you can configure and cannot see is worse than neither.
      

      

        Two collectors. A shop may have two systems, each with a collector, and this sheet
        describes one. Nothing here breaks — but the bin's alert scope is per-system (RFC §7.3)
        and a board serving two systems has one NeoPixel and two possible alert states, which is
        still undecided.
