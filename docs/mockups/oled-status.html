The Status Screen

A 0.96" SSD1306 (128×64, I²C) on the controller, so "is it working?" has an answer you can read while standing at the machine — without pulling out a phone. Every screen below is laid out on the real 21×8 character grid.

It works, on one board. As of 2026-08-21 a 0.96" SSD1306 answered at 0x3C on a DevKitC's GPIO16/4 and the firmware drew to it — the first display any DustGate board has driven. StatusScreenModel.h turns board facts into these exact rows, test_statusscreen.cpp asserts every screen below against the 21×8 budget on a host, and StatusScreen.h puts them on glass (pio run -e esp32dev_screen).

What that does not verify: the sleep and wake behaviour over hours, whether each layout below actually reads well on real glass at arm's length, and the pins proposed for the two node boards — those are still transcribed from published pinouts and have driven nothing. The screens on this page remain the design; the model and this page are the same design stated twice, so change a screen here, change the test.

The character budget

Adafruit_GFX's built-in font is 5×7 in a 6×8 cell. At size 1 that is 21 columns × 8 rows — and that is the whole design constraint. At size 2 a glyph occupies 2 columns and 2 rows, so a headline word costs half the screen height and you get 10 characters across.

Which is why "I'm connected to 3 gates, wifi signal good" can't be the screen. It's 41 characters of prose for a surface that holds 21 per line. The same facts fit easily once they stop being a sentence — that's the translation the layouts below are doing.

The header band is two rows, not one. A 6×8 signal glyph is about 1.5mm tall on a 0.96" panel — decoration rather than information — so it gets a 3×2-cell box instead, roughly four times the area, and the hostname sits centred beside it. That costs the one spare row every screen had. It was the right thing to spend it on: signal strength is half of what anyone walks over to check.

What the screens are doing

The big word is statusled::Status, verbatim

The board already has a status vocabulary — six states and four motion overlays in firmware/utils/StatusLed.h, each with a colour meaning. The screen does not invent a second one. It spells the same state the pixel is showing, and the detail lines below it explain that state. Two indicators that could ever disagree would be worse than one.

Motion outranks Status on the screen exactly as it does on the pixel: while a gate is moving, the move is the news.

It does not replace the pixel

The pixel is readable across a shop; this is readable at arm's length. Different jobs, both kept. The pixel answers "is something wrong?" from the far end of the room, the screen answers "what, specifically?" once you've walked over.

It sleeps, and waking it is a signal

OLEDs burn in, and a status screen with fixed labels lit 24/7 is the textbook case — the ghost of gates and nodes etched into every later screen. So the display blanks after a couple of minutes idle and wakes on events: a gate moving, a tool drawing power, a node dropping, any fault. A lit screen then means something happened rather than becoming wallpaper you stop seeing.

A fault holds it awake. Nobody should have to press anything to find out what broke.

The button wakes the screen, and does nothing else

Settled 2026-08-21, and built. Wake-on-event covers the cases that matter, so what a button buys is the deliberate wake — the board is fine, nothing is changing, and you want to read what a screen two feet away already knows. That case is common enough to be worth a pad.

Paging was rejected, not deferred. One edge, one wake: no long-press, no double-tap, no menu. A second gesture means a second thing it could mean, and a button that could change what the shop does would need every confirmation the web UI has — which is a different part with a different name. One screen per role is the honest answer.

Fitted with the panel rather than separately (-DHAS_STATUS_SCREEN defines all three pins), since a board with no screen has nothing for a button to wake. Driver: firmware/utils/WakeButton.h. Pins per board: DevKitC GPIO34 (input-only — needs an external 10kΩ pull-up), QT Py MISO/GPIO37, XIAO C5 D1/GPIO0. No button has been wired to a board yet.

Optional at build time — this is a product concern, not a bench one

Every DustGate ships without a screen unless someone fits one. So the display compiles out entirely when its pins aren't defined, the same seam every other optional part on these boards already uses — no display, no library, no flash spent.

Settled: a fitted screen is declared by the build (-DHAS_STATUS_SCREEN → the board header's own two pins) rather than discovered at 0x3C — and then probed at 0x3C anyway, to check the declaration is true. Probing would have been friendlier to someone adding one later; declaring is how every other fitted-or-not part on these boards is decided, and one seam beats two. A screen declared but not wired is still handled — no ACK, a line on serial, and the driver disables itself, because a missing panel must not hang the brain in Wire's timeout once per loop. That probe has to be ours: Adafruit_SSD1306::begin() checks nothing but its own malloc and reports success into an empty bus, which is how 2026-08-21 got SSD1306 up on a board with no panel on those pins.

2026-08-20 A status screen is worth adding, as an option "Is it connected?" currently requires a phone. On the primary that is a poor trade for a $2 part and two pins.
2026-08-20 The screen mirrors statusled::Status — it does not define its own states Two status vocabularies drift, and a screen disagreeing with the pixel beside it is worse than having neither.
2026-08-20 Sleep at idle, wake on event; a fault holds it awake Burn-in is real on a fixed-label screen, and a display that is only lit when something happened carries information by being lit.
2026-08-20 The signal glyph gets a two-row header band, not a single cell At 6×8 it is ~1.5mm on a 0.96" panel. Every screen had exactly one spare row and this is the best use of it — "is the wifi ok" is half of why anyone looks at the screen.
2026-08-21 The wake button is in, and paging is out The deliberate wake is the case wake-on-event can't cover, and it is worth one pad. Paging is a second meaning for the same button, on a device where anything that changes shop state needs the web UI's confirmations — so one edge, one wake, one screen per role.
2026-08-21 First panel driven — layouts survived contact with glass unchanged Three bugs stood between the design and a lit screen, none of them in the layouts: swapped SDA/SCL (scans identically to a dead module), Adafruit_SSD1306::begin() reporting success into an empty bus, and its periphBegin default silently moving I²C onto the stepper's pins. The 21×8 model needed no change, which is the argument for having written it first.
2026-08-20 The build stamp takes the spare eighth row — where there is one Provenance is worth a row nothing else wanted, and worth nothing at all if it can push a fact off the panel. Offered to every screen, taken only where the body used seven rows or fewer.
