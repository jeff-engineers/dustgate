# Audit — what to keep, what to restructure, what to cut (2026-11-23)

Read-only pass over every layer at `fbaccce`, judged by one question: **could a woodworker who follows basic
instructions set this up, change it, and recover when it goes wrong, without a terminal, a reflash or a shop reset?**
Today the answer is no. This file is the evidence and a proposed order; the decisions in §7 are Jeff's.

Size, for scale: app 28k lines (one component, `build.component.ts`, is 6.5k of them), the shared model 10k, firmware
~30k, the native brain 2.3k. 276 commits in the last 60 days, about 80 of them fixes.

## 1. Why the same kind of bug keeps coming back

Five causes. Each one produces bugs on its own; together they explain this morning.

**1.1 One fact, several copies, each cleaned up by hand.** The same fact is recorded in several places, and each edit
has to remember to update every copy. A gate's id can sit in ducts, a board's `chains`, the canvas cells and the wiring
view. A board's id can sit in gates, clamps, the collector and the pairing list. Nothing owns those references: the
canvas edits them directly, from many places. `build.component.ts` alone writes `parentBranch` 15 times, `setDucts`
5 times, `setElems` 4 times and `cells.delete` 6 times; `board-setup`, `selector-config`, `tool-setup`,
`collector-doc` and `servo-page` each edit the layout's boards, gates or plugs themselves. This morning's chain bug was
one path out of three that remembered. Every new reference (chains were the latest) has to be added to every path by
hand, and the only safety net is the validator at save time.

**1.2 Two brains.** The ESP32 brain is frozen but still built, tested and parity-checked: `firmware.ino` (4.4k lines,
the most-changed file in the repo with 55 commits in 60 days), `HttpApiServer.cpp` (2.2k), and the rule that everything
deciding anything lives in shared C++ so it could come back. That rule is why routing logic is written twice (JS in
`shared/device-model`, C++ in `firmware/control`) and held together by matched tests. About 7.5k lines exist only to
keep a brain nobody runs revivable.

**1.3 The shop's state is scattered, and nothing puts it back together.** What the shop "is" lives in five places:

| Where | What it holds |
|---|---|
| The brain's `topology.json` | the layout, including its own list of boards |
| The brain's `nodes.json` | a SECOND list of boards: the pairings |
| Each node | which brain owns it, what it was flashed as (PWM or bus) |
| Each bus servo's memory | its number, its mode, its limits |
| Each smart plug | which brain it reports to |

A layout change is adopted whole, which is good (`adoptLayout` in `native/src/main.cpp` rebuilds from the
document). But the other four places are only ever updated by a specific action, and **"Reset everything" clears just
the first two.** The nodes still think they belong to the brain, the servos keep their numbers and the plugs keep
reporting. That is why the reset this morning didn't help: it made the brain forget a shop the hardware still
remembered.

**1.4 The layout can't express "not decided yet", so the app decides for you.** Every gate must name a board
(`controllerId` is required). There is no "not wired", and dropping a cable on empty canvas does nothing
(`onWireUp`). So when a board changes from PWM to serial, its gates are stuck on a board that can't drive them. The
canvas refreshes the board's kind from what the board reports (`applyDrivesCache`) and offers no "this is a different
board now" or "unplug this gate". That's the blue line you couldn't break. The same shape recurs: a paired board must be
in the layout, a clamp must name a board, and so on.

**1.5 Too many kinds of hardware, multiplied through every path.** PWM servos, bus servos, the slider, the RF remote, a
CT clamp, a bin beam, smart plugs, and two brains. Each is a branch in pairing, the canvas, the board page, the
validator, the brain, the node and the docs. Mentions, roughly: plugs 175 files, CT 112, slider 100, PWM 68, bin 62,
RF 52. Every scenario you test multiplies by every option.

## 2. Cut candidates

Biggest win first. "Removes" is what goes away besides the code itself.

| Cut | Its own code | Spread | Removes | Replaced by |
|---|---|---|---|---|
| **ESP32 brain** | ~7.5k lines | 31 files | the parity check, the "decisions in shared C++" rule, the brain half of `firmware.ino`, `HttpApiServer`, the `*_primary` builds | nothing: the Pi is the brain (decided 2026-10-18) |
| **RF collector switching** | ~1.1k lines | 52 files | `RfCollectorPresser`, address guessing, HT12E bench, RF problems (`rf-gave-up`, `rf-send-failed`), the press-retry policy | a smart relay on the contactor coil, with a metering plug or the clamp for feedback (already allowed by the design constraints) |
| **PWM servos + custom carrier** | ~250 own lines, 446 mentioning lines | 68 files | channels, `referenceAngle`/pulse ranges, the 2-channel budget, the carrier wiring page, "PWM and bus never share a board" | bus servos on the Seeed bus board for every gate |
| **Slider** (question, not proposal) | ~1.5k lines | 100 files | homing, endstops, stepping mode, `positionMm` | ball valves on a trunk (your note: past 6–8 gates switch to ball valves anyway) |

The ESP32 brain is the safest cut and pays off immediately: it also frees the C++ core to be the brain's own code,
written once, rather than JS-and-C++ twins. RF is next, as you said. PWM + carrier makes every board the same
board, which collapses most of 1.5. The slider is the one I'd ask about rather than assume.

## 3. Keep

These have earned it: well tested, few fixes lately, and they decide things a woodworker never sees.

- **Routing and sequencing** (`shared/device-model/routing.js`, `sequencer.js`, `TopologyRouter.h`): never dead-head,
  make-before-break, most-recent-tool-wins.
- **Plug identity and claiming** (`plug-identity.js`, `plug-claim.js`) and the subnet sweep.
- **The CT trip** (`CtTrip.h`), validated to about 1% against two instruments.
- **NodeLink** as a protocol, slimmed once PWM and RF go.
- **The native brain's whole-document adopt** (`adoptLayout`): the right shape, to be extended (§4.3).
- **The scaffolding for a harness**: native brain with `--sim`, `fakenode`, `mock-node.js`, plug fakes, nine `e2e_*.sh`
  suites.

## 4. Restructure, layer by layer

**4.1 The shop model (`shared/device-model`): one owner per kind of thing.**
- A reference registry: every place each kind of id can appear, declared once.
- Operations built on it: `add`, `remove`, `rename`, `move`, `replaceBoard`, `unwire`. `removeSystem` calls
  `removeGate` for each gate; nothing filters arrays by hand.
- "Not wired" becomes a legal state for a gate (it routes as closed and is listed as needing a board), so the layout
  can always say what's true.
- A test runs every operation over every fixture and over random sequences, and asserts the shop is still valid and
  no id dangles.

**4.2 The app: screens call operations, never edit the document.**
- `build.component.ts` (6.5k lines) splits along what it does: drawing, ducts, wiring, boards, sheets. The edits move
  into the model's operations.
- `board-setup`, `selector-config`, `tool-setup`, `servo-page` and `collector-doc` do the same.
- One way to confirm, one way to undo, one sheet behaviour (this absorbs much of the UI review's zone 3).

**4.3 The brain: one list of boards, and reconcile everything.**
- The layout's boards ARE the pairings; `nodes.json` goes.
- On every change the brain works out what each node, servo and plug should be, compares, and corrects: a node's
  config, a servo's number and mode, a plug's reporting target. Unpair, replace, reflash and reset are all just "the
  layout changed".
- **Reset reaches the hardware**: it releases every node and plug it owns. Then a reset actually starts over.

**4.4 The node firmware: one kind of board.** Once PWM and RF go, a node is a bus board with an optional clamp and
optional bin beam. `dustgate_node.cpp` (2.3k lines) shrinks to match.

## 5. What a woodworker should be able to do, and today can't

Each of these needs a plain-English remedy in the app, with no terminal, no reflash and no reset.

| Situation | Today | Should be |
|---|---|---|
| A board was reflashed from PWM to serial | gates stuck on it; no way to unplug them; save refused (now warns) | the app sees the change and asks: "Serial 1 is now a serial board. Its 2 gates need serial servos — re-wire them, or move them to another board." Gates go to "not wired" until then |
| Swap a dead board for a new one | pair the new one, re-cable every gate by hand, delete the old | "Replace board" moves everything from the old board to the new one in one step |
| Rearrange servos on the bus | numbers are shop-wide and live in the servo; renumbering is a developer page | drag the gate to its new socket; the brain renumbers the servo itself (reconcile) |
| Start over | "reset" clears the brain only; boards and plugs refuse the next pairing | reset releases every board and plug, then says "Your boards and plugs are free. Pair them again from Boards." |
| A board goes offline | "Board X is offline" plus a duration | what it means for the tools ("the Planer won't get suction"), and what to check: power, then WiFi, then "the light on the board" |
| A plug got a new address | found again by the sweep, if lucky | found automatically, with "Found the Planer's plug again" in the log |

Every problem the brain raises gets three parts: what happened, what it means for the tools, what to do, written
for someone who has never seen a terminal. Today the five node-side problems (`DeviceProblems.h`) say what happened,
and some say what it means, but few say what to do. One still says "controller".

## 6. The harness

On the existing scaffolding: the real native brain with `--sim`, simulated nodes, fake plugs, a scratch state dir.
Each scenario is a script of things a person does, checked after every step against what must always hold:

- the collector never runs against all-closed gates
- every running tool has an open path
- the layout saved is the layout the brain runs
- no problem is left standing that the step resolved
- every board, servo and plug the layout names is reachable and configured the way the layout says

Scenarios to start with (yours):
1. Draw a shop from nothing; pair boards; save; run each tool.
2. Change the whole layout: move tools, add and remove systems.
3. Reuse a node in a new place, without reflashing.
4. Reflash a node from PWM to serial (if PWM survives) / swap a dead board for a new one.
5. Rearrange servos along a chain, and between chains.
6. Unpair a board, pair it again.
7. Delete a system while a tool is running.
8. Reset, and set the shop up again.
9. A plug changes address; a board drops off WiFi and comes back.

Then a randomized version: hundreds of random edit sequences, same checks. The harness runs in CI. There is
no known-good release yet; the first build that passes it becomes the first one, and from then on only a passing,
tagged build goes to the shop.

## 7. Decisions needed (Jeff)

1. **Cut the ESP32 brain** entirely, including the parity check and the shared-C++ rule? (Recommended: yes, first.)
2. **Cut RF collector switching**? What replaces it: a smart relay on the contactor coil, with feedback from a
   metering plug or the clamp?
3. **Cut PWM servos and the custom carrier**: every gate on a bus servo, every board the Seeed bus board?
4. **The slider**: keep, or ball valves only?
5. **Order**: proposed: cuts (1–3) → model owners and "not wired" (4.1) → harness (§6) → app (4.2) → brain reconcile
   (4.3) → UI review findings that survive. Cutting first means everything after it is smaller.
6. **Shop time**: there is no known-good release yet, so nothing to tag. The first build that passes the harness's
   core scenarios (§6, 1–4) becomes it, and shop time stays on it from then on.
