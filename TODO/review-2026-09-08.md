A full pass over the project. Findings are grouped by zone and **ordered by
criticality within each zone** — the first item in a list is the one to fix
first.

Written against `9c9d8fc`, then re-verified against `8a6b917` (current `main`)
before any fix was made. The three commits that landed in between — the seam
feature, the charset pass, and the archive/TODO tick — touched only

file and line it names. All suites were green at both points, so nothing here is

Severity labels: **[C]** critical (physical damage, data loss, or the hard
design rule broken), **[H]** high, **[M]** medium, **[L]** low / polish.

## How this list gets worked

Standing process, also written up as the `burndown` skill (`.claude/skills/burndown/`)
so a cold session picks it up the same way:

1. Branch off a freshly pulled `main` — never work on `main`.
2. Take findings in **criticality order**, and inside a tier prefer the ones
   that are well defined and cheap to verify.
3. **One commit per fix**, explaining why, with the review section as its last
   line.
4. Verify per fix, not at the end (see the `verify` skill for which suites).
5. **Tick the finding off in the same commit as the fix** — the heading stays,
   the body becomes a `FIXED` line. Headings are cross-referenced by number, so
   nothing gets renumbered.
6. Anything needing Jeff at the bench gets flagged, not guessed at.

## 1. Firmware — control and routing

### 1.1 [C] C++ routing ignores `role: "blocked"` — a tool can be routed into a capped branch

`shared/device-model/routing.js` `pathToCollector()`:

```js
const branch = (parent.branches || []).find((b) => b.id === duct.parentBranch);
if (!branch || branch.role === 'blocked') return null;
```

`firmware/control/TopologyRouter.h` `_pathToCollector()` does **neither** check.
A missing branch falls silently through (`cur = parentId`) with no hop pushed; a
`role: "blocked"` branch is walked as if it were a tool branch.

Consequences, in order of seriousness: the selector is left at its closed state
while the tool is reported `reachable: true`, so `TopologyRuntime` sees no failed
make, nothing blocks the blower, and it starts into a sealed system. That is the
one rule the project says it will not break. Secondarily, firmware and model
disagree about the same document, which is what the anti-drift discipline exists
to prevent.

The `feedChain` fixture already carries a `role: "blocked"` branch (`b3`), so the
shape is modelled — nothing is ducted to it, which is why the parity suite
passes.

This is a `nodelink.test.js`↔`test_nodebus.cpp`-style pair in everything but
name, and it has drifted.

### 1.2 [C] Nine `std::string` constructions from a possibly-null `const char*`

**FIXED 2026-09-08** — *Stop a malformed layout from crashing the board on every
boot.* All ten sites (there were ten, not nine — `TopologyRuntime.h` had two on
the same line text) now go through a `_str()` helper, and an unnamed element is
dropped from the index rather than keyed on `""`. Covered by a new
malformed-document case in `test_topology_router.cpp`; host tests 20/20 and
`xiao_c5_primary` compiles.

### 1.3 [H] `parseSetFrame()` does not bound `positionMm`, while the JS validator does

`nodelink.js` `validateFrame()` rejects non-numbers and NaN and bounds linear
moves to `-10000..10000`. `control/NodeLink.h` `parseSetFrame()` bounds the servo
angle to 0–180 but accepts **any** `positionMm`.

The node then computes
`(long)(cmd.positionMm * ST3215_COUNTS_PER_MM * -HOME_DIRECTION)` and hands it to
`moveTo()`. NaN there is UB in the float→long conversion; a huge value is clamped
to `kMaxStepsPerCommand` and re-issued chunk after chunk until the runaway guard
or the carriage stops it. The whole stated safety story for a node is "it moves
only when told exactly where", and this is the one field where it isn't checked.

Mirror the JS bounds — two lines.

### 1.4 [M] `RemoteActuatorBus::jog()` can discard a routed move and stall the shop for 210 s

`_txFrame` is a single slot. `setState()` sets `_txPending` **and**
`_moveOutstanding`; `jog()` overwrites `_txFrame` and sets `_txPending` but
deliberately leaves `_moveOutstanding` alone.

A jog issued between a `setState()` and the task's next drain therefore throws the
routed SET away while leaving `_moveOutstanding` set, so the primary blocks the
shop-wide move queue for `kMoveTimeoutMs` — now 210 seconds. Reachable from the
gate configurator: jogging a servo on a node while a tool starts elsewhere.

At minimum, refuse a jog while `_moveOutstanding` is set, or clear
`_moveOutstanding` when the frame it belongs to is overwritten.

### 1.5 [L] `RemoteActuatorBus` ignores `WStype_ERROR`

`onEvent()` handles `CONNECTED`, `DISCONNECTED`, `TEXT`, `PING`, `PONG` and lets
everything else hit `default: break;`. A socket error leaves `_connected` true
until the six-second pong timeout, where the disconnect path clears it
immediately. Treating `ERROR` like `DISCONNECTED` makes the two failure modes
report at the same speed.

### 1.6 [L] `localBinSystemId()` lets an unidentified board claim someone else's bin

`utils/BinSensor.h`:

```cpp
if (!cid || own.empty() || own == cid) return std::string(sys["id"] | "");
```

The stated rule, and the one `NodeBus` implements, is "absent, or equal to this
board's own id, means local". The extra `own.empty()` clause means a board that
does not yet know its own controllerId reports the **first** bin sensor in the
document as its own, whoever it is wired to.

### 1.7 [L] `CollectorState` is brace-initialised with 10 of its 12 members

`TopologyRuntime::adopt()`:

```cpp
CollectorState{false, false, 0, false, false, false, false, false, 0.0f, 0};
```

`binKnown` and `binFull` fall to value-initialisation, which happens to be
correct today. But the struct carries an explicit comment about *why* it has no
default member initializers (gnu++11 aggregate rules), which makes a positional
initialiser that silently stops two members short exactly the thing that breaks
when someone inserts a field. List all twelve, or add `= {}`.

## 2. Firmware — slider and motion

### 2.1 [C] The `HOME_FAILED` retry loop re-sweeps forever and destroys the servo's EEPROM

**PARTLY FIXED 2026-09-08** — *Stop retrying a drive that is already answering.*
The re-sweep loop is closed and the button hold now clears a failed home, so
there is still a way back without a power cycle. Compiles for `xiao_c5_linear`;
not bench-tested.

**Still open:** `ST3215Bus::writeEeprom8/16` still write unconditionally, so
`begin()` rewrites the mode and both angle limits on every call. That is now
bounded — `begin()` runs once at boot and only on a genuine reconnect — but a
read-before-write is still the right thing and is a separate change.

### 2.2 [C] `ST3215LinearDriver::reconnect()` leaves `_torque` stale — a re-plugged servo comes back dead

**FIXED 2026-09-08** — *Reset torque state when the slider's bus servo reconnects.* Compiles for `xiao_c5_linear`; not bench-tested.

### 2.3 [H] `LimitSwitchDistance` starts the sweep while the release move is still in flight

`updateHoming()`, RELEASING phase: as soon as `datumTriggered` goes false it does
`_phase = SEEKING; _motor->startHoming();`. But the 15 mm release move is still
running at that moment — the switch clears part-way through it, not at its end.

That matters specifically on this servo, and this file is the one that says so:
"a new command DOES NOT SUPERSEDE the one in flight". Worse,
`startHoming()` computes `_target = _position + sweep * HOME_DIRECTION` from the
**committed** `_position`, not from `livePosition()` the way `moveTo()` carefully
does — so the sweep target is stale by however far the release travelled, and
`sendNextChunk()` then resets `_chunkStart`/`_chunkEnd`/`_lastRemaining` under a
command still retiring, corrupting `livePosition()` until it settles.

Cleanest fix is `_motor->stop()` before `startHoming()`, which is what the phase
already does on entry. Failing that, `startHoming()` should refresh
`_position = livePosition()` exactly as `moveTo()` does — that inconsistency is
worth closing regardless.

### 2.4 [M] `_zeroTravelRetires` is never reset when a new move starts

**FIXED 2026-09-08** — *Scope the slider's zero-travel fault counter to one move.* Compiles for `xiao_c5_linear`.

### 2.5 [M] The node's screen reports slider position with the wrong sign

`node/dustgate_node.cpp` (`updateStatusScreen`):

```cpp
f.sliderMm = motor.getPosition() / ST3215_COUNTS_PER_MM;
```

Every other steps→mm conversion in the tree also divides by `(-HOME_DIRECTION)` —
`firmware.ino:1769`, `firmware.ino:2853`, `api/HttpApiServer.cpp:1333`,
`SerialDebugControl.cpp:701` — because `moveTo()` multiplies by `-HOME_DIRECTION`
on the way in. With the node's default `g_homeIsMaxEndstop = false`,
`HOME_DIRECTION` is `+1`, so the screen shows the negation: a gate at 250 mm reads
`-250`.

Display-only, but the screen is the node's whole UI and this is the number
someone reads while deciding whether homing worked.

### 2.6 [L] `LimitSwitchDistance::updateHoming()` blocks for 20 ms mid-sweep

The `delay(20)` after the datum trip sits inside a state machine whose whole
justification is that it is ticked from `loop()` and never blocks (the node's
watchdog note is explicit). 20 ms against a 10 s watchdog is harmless today; it
is the precedent worth not setting.

### 2.7 [L] Two different things are both named `kMoveTimeoutMs`

`topo::nodelink::kMoveTimeoutMs` is 210 000 ms (the primary giving up on a node);
the file-static `kMoveTimeoutMs` in `ST3215LinearDriver.cpp` is 120 000 ms (one
bus command's fault backstop). Different scopes, so it compiles — but
`node/dustgate_node.cpp` reasons about the first in a `static_assert` a few
hundred lines from where the second governs the hardware. Renaming the driver's
to `kCommandTimeoutMs` costs nothing and removes a real trap.

## 3. Shared model, mocks and protocol

### 3.1 [H] `demo-api.service.ts` is missing the manual-wattage floor its two twins have

CLAUDE.md's table names this a three-way pair. The firmware (`manualWattsFor()`,
TopologyRuntime.h) and `tools/mock-api.js` both read
`threshold > 0 ? threshold * 3 : 15` — the floor exists so "manually on" can never
be indistinguishable from "drawing nothing".

`dustgate-ui/src/app/services/demo-api.service.ts:196` is `Math.round(trip * 3)`
with no floor. `toolThreshold()` returns an explicit `thresholdW: 0` as `0`, so a
machine configured that way reads 0 W in the demo when switched on by hand —
exactly the failure the C++ comment documents.

### 3.2 [M] Two unregistered JS↔C++ constant pairs

Both are the shape CLAUDE.md's table exists to catch:

- `tools/mock-api.js` refuses a fourth board with a bare `pairedNodes.length >= 3`.
  The device's number is `kMaxPairedNodes` (`control/NodeRegistry.h:38`). Nothing
  on either side points at the other.
- `tools/mock-api.js`'s `/api/servo/jog` range-checks `ch < 0 || ch >= 4`. That 4
  is `MAX_SERVOS_PER_HOST` (topology.js:39) / `SERVO_COUNT` (config.h:270) — a
  pair the table already tracks, restated a third time as a literal.

The mock already `require`s three model files, so the second is a one-line fix.
The first wants a row in the table, or a shared constant.

Every pair the table *does* list currently agrees — see §8.

### 3.3 [L] `tools/mock-api.js` applies `runModel()` unevenly

`/api/setstop`, `/api/move`, `/api/jog` and the outlet routes wrap their model
call in `runModel()` so a thrown model error becomes an HTTP status.
`/api/config/orientation`, `/api/config/gates`, `/api/config/idle-timeout` and
`/api/dustcollector/switch` do not, so a model throw there becomes an unhandled
exception and a dead socket rather than a 400. Nothing currently throws from
those paths, which is why it hasn't bitten.

### 3.4 [L] Small mock tidiness

`outletPut` and `outletDel` in `mock-api.js` compile the identical regex twice a
few lines apart; `mock-node.js`'s `holdAtRest` is declared `let` and never
reassigned.

## 4. GUI — Angular app

### 4.1 [H] The Live view never recovers if the first topology fetch fails

`live/live.component.ts` `ngOnInit()`:

```ts
try {
  await this.api.whenReady();
  const topo = toShop(await this.api.getTopology());
  if (topo) this.parseTopology(topo as unknown as Topology);
} catch {
  this.tools = [];      // no topology → empty state
  return;               // ← and the poll is never started
}
await this.refresh();
this.poll = setInterval(...);
```

A device still booting, a transient 404, or a dropped request leaves the **daily
driver screen** permanently empty with no retry — the only way back is a manual
page reload. `build.component.ts` gets this right: it polls regardless of whether
the initial fetch succeeded.

Secondary: the `try` also wraps `parseTopology()`, so a genuine parse bug is
swallowed as "no topology configured" rather than surfacing.

### 4.2 [H] `SettingsComponent` leaks a subscription on every visit

`settings/settings.component.ts:339` subscribes to `api.ready$` — a
`BehaviorSubject` that lives for the app's lifetime — and the class
`implements OnInit` only, with no `ngOnDestroy` and no `take(1)`. Every visit to
/settings adds a permanent subscription whose callback resets `numGates` and calls
`markForCheck()` on a destroyed component.

It only wants the first `true`, so `firstValueFrom(ready$.pipe(filter(Boolean),
take(1)))` — or just `await this.api.whenReady()`, which already exists for
exactly this — is both the fix and the smaller code.

### 4.3 [M] `ApiService`'s WebSocket `onerror` closes the wrong socket

```ts
this.ws.onerror = () => { this.ws?.close(); };
```

The handler is bound to one socket but acts on the `this.ws` **field**. After a
reconnect that field points at a newer socket, so a late error from the stale one
closes the live connection — which then schedules another reconnect, and so on.
Close the socket the event fired on (`ev.target`), or capture the socket in the
closure.

### 4.4 [M] The stop-conflict message is written carefully and then thrown away

`ApiService.checkStopConflict()` throws a genuinely useful `Error`:

> `This looks too close to Gate 3's saved position (125.4 mm) — jog further away before saving.`

`saveStop()` calls it synchronously, so it throws before any HTTP. The one caller,
`gates/linear-calibration.component.ts:350`, reads the message as
`(e as {error?:{error?:string}})?.error?.error` — the *HTTP* error shape. A plain
`Error` has no `.error`, so it falls through to the generic
"Couldn't save that position — it may be too close to another outlet." The
specific gate number and position never reach the user.

Also in that path: `checkStopConflict` defaults `positionMM` to `0` when absent,
so on firmware that doesn't publish it, every save is compared against 0 mm.

### 4.5 [M] `toggleCollector()` claims "nothing was switched" after a partial failure

`live/live.component.ts` `toggleCollector()`, off path:

```ts
for (const t of g.tools) if (t.on) await this.api.setToolManual(t.id, false);
if (g.manual) await this.api.setCollectorManual(false, g.id);
```

If the third of five tools fails, the first two are already off, and the catch
sets `"Couldn't reach the controller — nothing was switched."` — which is false,
and misleading in the direction that matters (the user believes the shop is in
the state it was, and it isn't).

### 4.6 [L] `separateLanes()` judges later lane groups against already-nudged geometry

`build/routing/router.ts`. All group keys are computed up front from the original
points, then each group mutates points in place. A segment's `span()` in a later
group is therefore read *after* a perpendicular group may have moved its
endpoints, so the overlap test runs on shifted extents while the grouping used the
original line. Order-dependent, and it makes the result sensitive to
`Map` iteration order.

Lower confidence than the rest of this list — I did not build a repro — but the
mutate-while-iterating-derived-state shape is worth a look.

### 4.7 [L] `routeAllShared()` has an unreachable tail

```ts
if (best) return best;
const last = routePass(scene, opts, order);
return { out: separateLanes(last.out), lattice: last.out, shared: [] };
```

`best` is assigned on every iteration where `drawn.length > 0`, and the loop
returns early when it is 0 — so `best` is always set by the time the loop exits
and the two lines after it never run. (They also report `shared: []`
unconditionally, which would be a lie if they did.)

### 4.8 [L] Repeated work in hot paths

`shop-doc.ts` `machineIdOfPort()` scans every element of every system, and
`outletTakenByAnotherMachine()` calls it inside a `.some()` over rows — O(rows² ×
elements) on every keystroke in the picker. `healMachineNames()` calls
`primaryPortOf()` per machine, each of which rebuilds the whole
`portsByMachine` map. `live.component.ts` `collectorSub()` calls
`collectorChip(g)` twice in succession.

Also: `refresh()` has no in-flight guard of its own (the `busy` flag it checks is
set only by user actions), so a `getStatus()` slower than the 2 s poll can have
two responses applied out of order.

## 5. Build, deploy and test tooling

### 5.1 [C] The topology backup is disabled, so every filesystem flash silently erases the shop

`deploy.sh` explains the hazard itself at line 74:

> topology.json lives in the same LittleFS partition as the Angular bundle, and
> `pio run --target uploadfs` writes a fresh image built from firmware/data/. So
> every filesystem flash silently erases the user's shop — layout, gate
> calibration, node links, plug pairings.

Both call sites are commented out (lines 351 and 582), with a dated note
explaining the reasoning (the abort-on-unreachable was worse for bench work than
the loss it prevented). That reasoning is sound for a bench, and matches "the shop
is not yet in service" — but it is currently the single highest-consequence thing
in the repo, and the note's own "what to decide when revisiting" already names the
fix: ask `/api/topology` first, skip quietly on 404, and never abort a deploy over
a board with nothing to lose.

Listed as critical not because it is wrong today but because the day the shop goes
into service it becomes data loss on the next `dev.sh flash`, and nothing in the
tool will warn.

Meanwhile `backup_topology()`, the restore block, `DO_TOPO_BACKUP` and the
`--no-topology-backup` flag are all still live code with no effect — see §7.

### 5.2 [M] `deploy.sh` wipes `firmware/data` without ensuring it exists

**FIXED 2026-09-08** — folded into *Stop tracking the generated LittleFS bundle*, since the two only make sense together.

### 5.3 [M] `spec-runner.js` keeps a hand-maintained suite list

`SUITES` names nine files explicitly; `router.spec.ts` and `wire-geometry.spec.ts`
are run by the separate `test:routing`/`test:wiring` scripts. All eleven specs are
covered *today*, but a new `*.spec.ts` silently never runs until someone
remembers to add it — and a spec that never runs is worse than no spec, because
it looks like coverage. Globbing `.spec-test/**/*.spec.js` would close it.

### 5.4 [L] Inconsistent cleanup in the conformance CI scripts

`nodelink:conformance:ci` ends with `kill $NODE_PID 2>/dev/null`;
`conformance:ci` and `topology:conformance:ci` use a bare `kill $MOCK_PID`, which
prints a spurious error if the mock already exited. Same shape, three spellings.

### 5.5 [L] `.gitignore` still lists `.pio/`

`platformio.ini` pins `build_dir`/`libdeps_dir` under `.pio.nosync/`, and only
`.pio.nosync` exists here. The `.pio/` line is vestigial. (Harmless — noting it
only because the surrounding comment in that file is careful about exactly this
kind of thing.)

## 6. Docs and design record

### 6.1 [H] CLAUDE.md points at the wrong file for the decision log

CLAUDE.md's "UI work" section says:

> `docs/mockups/canvas.html` is the canonical canvas design **and the only place
> decisions are recorded** … It carries the line/glyph vocabulary, the port and
> system rules, the drag rules, **and a dated decision log**.
> … A settled question does not get a new page: change the section it affects and
> **add a row to the decision log**.

`canvas.html` has no decision log. It has five `Built · <date>` pills and no
register. The actual decision register is **`docs/mockups/decisions.html`** — 75

> `canvas.html` is the canonical canvas design; this register is the canonical

`decisions.html` is not mentioned in CLAUDE.md at all. Anyone (person or model)
following CLAUDE.md adds their decision row to the wrong file — which is the
precise drift the document's own "this table is a cache, keep it honest or delete

Fix is one paragraph in CLAUDE.md naming both files and what each is for.

### 6.2 [M] Four decision logs now exist

Beyond `decisions.html` (75 entries), three live mockups each maintain their own
dated "Decision log": `shop-status-chips.html` (30), `oled-status.html` (26),
`gates-list.html` (10). At least one subject — the shop page's per-system
collector cards — is written up in both `decisions.html` and
`shop-status-chips.html`.

This is the "seven mockups that disagreed with each other" situation CLAUDE.md
says cost three re-litigations, re-forming. Either fold the per-page logs into the
register, or state in CLAUDE.md that a screen-specific page owns its own log and
the register owns cross-cutting decisions — but pick one.

### 6.3 [L] CLAUDE.md's size hint for `build.component.ts` is stale

It says "~4k lines — grep it, don't read it whole". It is 5 711. The advice is
still right and more so; the number just wants updating.

## 7. Dead code, all zones

### 7.1 [M] `deploy.sh`'s backup machinery is live code with no call sites

`backup_topology()` (line 132), the restore block, `DO_TOPO_BACKUP` (243) and the
`--no-topology-backup` flag (256) all still exist and do nothing — both call sites
are commented out. The usage header does say "no-op since 2026-08-22", so this is
documented rather than forgotten, but a flag a user can pass that has no effect is
worth either restoring or removing. See §5.1.

### 7.2 [M] `firmware/data/` is a committed Angular build artifact

**FIXED 2026-09-08** — *Stop tracking the generated LittleFS bundle.* Kept on disk; `.gitignore` line taken, `deploy.sh` now `mkdir -p`s the directory.

### 7.3 [L] The v1 spelling aliases have no call sites left

`control/TopologyRuntime.h` keeps five "v1 spellings, kept for call sites that
predate ports". Three have no remaining caller anywhere in the tree:

- `hasTool()` — TopologyRuntime.h:311
- `toolIsManual()` — TopologyRuntime.h:312
- `activeTools()` — TopologyRuntime.h:445 **and** TopologyController.h:205

(`setToolPower`, `setToolManual` and `toolForOutlet` are still called and should
stay.) Deleting the three keeps the comment above them honest.

### 7.4 [L] `LimitSwitchDistance::_releaseStart` and `Phase::BACKING_OFF` are vestigial

`_releaseStart` is documented as "position when the release began, to bound it",
but nothing bounds anything with it — the release is bounded by
`!_motor->isMoving()`. It survives only as a "have we started" sentinel, complete
with `if (_releaseStart == 0) _releaseStart = 1;` to dodge its own zero. A plain
`bool _releasing` says what is meant.

Separately, `_phase` is only ever assigned `RELEASING`, `SEEKING` and `DONE`;
`BACKING_OFF` is unreachable because that state is tracked by the parallel
`_backingOff` bool. Two variables for one state machine, one value never used.

### 7.5 [L] Miscellaneous unreferenced symbols

- `ST3215LinearDriver::lastStopMethod()` — the member is used (`printDriverRegs()`
  reads `_lastStopMethod` directly), the public accessor never is.
- `controllerIndex()` — `shared/device-model/topology.js:156`, exported at :790,
  referenced nowhere in `shared/`, `tools/` or `dustgate-ui/src/`.
- The unreachable tail of `routeAllShared()` — see §4.7.
- `activeTools` in `topology-device.js` is a v1 alias with no consumers; unlike
  the C++ ones it is part of the published model surface, so this one is a
  judgement call rather than clearly dead.

## 8. Checked and found clean

Recorded so the next reader doesn't re-derive them.

- **Every constant pair in CLAUDE.md's table currently agrees**: off-delay 5000,
  threshold 5 W, servo bank 4, `NUM_STOPS` 8 (and even, per the `static_assert`),
  separation 10 mm, idle timeout 3600, both manifold pitches, and all five
  NodeLink timings. Also `MAX_SLIDE_BRANCHES` (8) = `SLIDE_MAX_OUTLETS` (8) =
  `NUM_STOPS` (8), the three-way that was wrong on 2026-09-05.
- **HTTP route registration order** in `api/HttpApiServer.cpp` is correct with
  respect to the ESPAsyncWebServer prefix-matching trap the mock warns about:
  `/api/nodes/discover` and `/api/nodes/pair` both precede `/api/nodes`, and
  `/api/outlets/discover` precedes `/api/outlets`. Every remaining prefix overlap
  is separated by HTTP method.
- **Coast expiry** in `TopologyRuntime::update()` uses
  `(int32_t)(nowMs - c.coastUntilMs) >= 0`, which handles `millis()` wraparound
  correctly, and the documented "a caller that passes a constant simply never
  coasts" behaviour does hold.
- **`nodeWs.cleanupClients()`** in the node's `loop()` is load-bearing, as its
  comment says; nothing else reaps disconnected WebSocket clients.
- **Component teardown** is good: `live`, `build`, `board-setup` and
  `linear-calibration` all clear their intervals and unsubscribe. `settings` is
  the one exception (§4.2); `app.component`'s subscription is root-lifetime and
  fine.
- **TypeScript is strict** — `strict`, `noImplicitOverride`,
  `noPropertyAccessFromIndexSignature`, `noImplicitReturns`,
  `noFallthroughCasesInSwitch` — with only six `any`/`ts-ignore` escapes in the
  whole app.
